# FavaBench 샘플 데이터 분석 및 측면 기반 평가(Aspect-based Evaluation) 작동 원리

이 문서는 FavaBench의 구조를 해부하고, "측면 전담 경량 모델(SLM)이 어떻게 LLM의 답변 전체를 받아 세밀하게 평가를 수행하는가?"에 대한 근본적인 작동 방식을 설명합니다.

---

## 1. FavaBench 샘플 데이터 구조 해부

샘플 파일(`favabench_sample.json`)에 있는 한 데이터(Amdavad ni Gufa 관련 질문)를 기준으로 각 필드의 의미를 설명합니다.

- **`prompt` (질문):** 사용자가 LLM에게 던진 지시문입니다.
  - _예:_ "Amdavad ni Gufa에 대해 설명해 줘. (위치, 국가 포함)"
- **`output` (평가 대상 LLM의 원본 답변):** ChatGPT 등 평가를 받아야 하는 LLM이 만들어낸 **'날것의 전체 텍스트'**입니다. 이 텍스트 안에는 맞는 말과 환각(거짓말)이 교묘하게 섞여 있습니다.
- **`annotated` (인간 전문가가 만든 '정답지'):** 측면 기반 평가의 핵심입니다. 인간 전문가가 `output` 텍스트를 읽고, **환각이 발생한 정확한 위치(Span)에 XML 태그를 달아 오류 유형과 수정 방향을 명시해 둔 텍스트**입니다.

---

## 2. 세밀한 환각 평가는 대체 "어떻게" 이루어지는가?

질문하신 **"output 전체를 던지면 알아서 평가하는 것인가?"**에 대한 대답은 **"그렇습니다. 단, 결과물을 내뱉는 형태가 완전히 다릅니다."**입니다.

### 기존 거대 모델 기반 평가 (Coarse-grained)

- **입력:** Output 전체 텍스트
- **출력:** "이 답변은 환각을 포함하므로 0점입니다." (이유를 장황하게 글로 설명하지만, 시스템적으로 오류 위치를 콕 집어내진 못함)

### FAVA 방식의 세밀한 측면 평가 모델 (Fine-grained)

우리가 만들고자 하는 경량 '판사 모델'은 Output 전체를 입력으로 받습니다. 하지만 평가 결과를 점수나 긴 글로 내뱉는 것이 아니라, **오류 부위에 색칠(태깅)을 한 텍스트를 통째로 다시 뱉어내도록(Text-to-Text) 파인튜닝** 됩니다.

판사 모델에 Output 전체를 던졌을 때 기대하는 동작은 다음과 같습니다:

1.  **입력 (판사 모델에게 던짐):** "The gallery is a popular tourist attraction and has won several architecture and design awards."
2.  **출력 (판사 모델이 내뱉은 평가 결과):** `<unverifiable><delete>The gallery is a popular tourist attraction and has won several architecture and design awards.</delete></unverifiable>`

즉, 판사 모델은 **"텍스트의 어느 위치에서, 어떤 측면의 오류가 발생했으니, 어떻게 지우거나 수정하라"**는 명시적인 기호(XML 태그)를 뱉어내도록 훈련받는 것입니다.

---

## 3. 샘플에서 발견된 주요 오류 측면(Aspect) 태그 분석

FavaBench 샘플의 `annotated` 필드에는 다음과 같은 태그들이 달렸습니다. 인간 전문가가 어떻게 라벨링했는지, 판사 모델이 추후 어떻게 뱉어내야 하는지를 보여줍니다.

**① 주관적 개입 오류 (Subjective Error)**

- **태그:** `<subjective><delete> ... </delete></subjective>`
- **상황:** 위키백과처럼 객관적인 정보만 달라고 했는데, LLM이 임의로 평가를 섞은 경우입니다. 전문가(또는 훈련된 판사 모델)는 이 부분을 `<delete>` 처리해 버립니다.

**② 검증 불가 헛소리 (Unverifiable Error)**

- **태그:** `<unverifiable><delete> 건축과 디자인 상을 여러 개 받았다. </delete></unverifiable>`
- **상황:** 그럴싸하지만 사실 확인할 길이 명확하지 않은 내용을 LLM이 지어냈을 때 감지합니다.

**③ 관계 및 팩트 오류 (Relational Error) - 가장 중요!**

- **원본 문장:** "월요일 빼고 다 열고 무료입니다."
- **태그:** `<relation><delete> 매일 열고 무료다 </delete><mark> 공휴일과 월요일 빼고 매일 열고 무료다. </mark></relation>`
- **상황:** 부분적으로 맞지만 관계나 조건에서 팩트가 틀린 경우입니다. 이 태그는 단순히 지우는 것(`<delete>`)을 넘어 올바른 정보로 대체(`<mark>`)하는 수정안까지 제시합니다.

---

## 4. 이 방식을 우리의 아이디어에 적용한다면?

질문자님이 구상하신 **"숫자의 일관성만 보는 모델", "도메인 단어만 보는 모델" 구축**에 이 메커니즘을 100% 동일하게 가져갈 수 있습니다.

예를 들어 **'수치 검증 전담 경량 모델'**을 만든다고 가정해 보겠습니다.

1.  **학습 준비:** 재무제표 RAG 질문에서 숫자를 교묘하게 틀리게 말한 데이터 수천 개를 만듭니다.
2.  **정답지(태깅) 작성:** `<numerical_error><delete>영업이익 50억</delete><mark>영업이익 20억</mark></numerical_error>` 와 같이 정답지를 만듭니다.
3.  **모델 파인튜닝:** Llama-3 (8B) 같은 경량 모델에게 "재무 정보(Context)"와 "LLM의 Output 전체"를 던져주고, 위와 같은 태그가 달린 문자열을 출력하도록 훈련(Fine-tuning)시킵니다.
4.  **실전 활용:** 파인튜닝이 끝나면, 사용자는 복잡한 로직 없이 **LLM의 답변(Output) 전체를 판사 모델에게 툭 던지면 끝**납니다. 판사 모델은 알아서 문장을 스르륵 읽다가 숫자가 틀린 부분을 귀신같이 찾아내어 XML 태그로 감싸서 뱉어줄 것입니다. 우리는 정규표현식(Regex)으로 태그 부분만 쏙 파싱하면, 시스템이 완벽하게 환각의 위치와 종류를 기록할 수 있게 됩니다.
